## 1. Purpose and evidence standard

This is a **cross-milestone technical qualification ledger** for the current `v1.12.0` implementation, not a replacement for an original validation log, the generated workload-baseline evidence package, or a security assurance opinion. It records the implementation boundary, concrete observations, provenance, gaps, and release gates for:

- **M1:** optional application ECS task-role managed policy attachments;
- **M2:** optional ECS-native container health checks;
- **M3:** optional additional regional Interface VPC Endpoints; and
- **M4:** integration regression, application release workflow, documentation, and final readiness.

A reported success is distinguished from independently retained machine output and from a test that has **not** been performed or evidenced. Historical evidence remains attached to its original environment, revision, and configuration. Neither merging a PR nor obtaining `16/16` workload validators retroactively executes a behavioral test on the final release commit.

Terminology used below:

| Label | Meaning |
|---|---|
| **Implemented** | Reviewed capability exists in the identified Git commit or PR. |
| **Offline tested** | Mocked/unit-style scenarios ran successfully; no live service interaction is implied. |
| **Live observed** | An actual AWS response or workload execution was supplied and reviewed. |
| **Operator reported** | Maintainer confirmed the outcome, but complete original command output or export package was not retained in this document. |
| **Pending** | A roadmap acceptance requirement or supporting provenance still needs completion/review. |
| **Deferred (explicit exception)** | A planned acceptance exercise has been intentionally postponed by the maintainer; existing evidence and the untested boundary must remain visible. |
| **Not tested / out of scope** | No qualification claim is made for that path. |

## 4. M1 — Extensible ECS task IAM

### Implementation and observed validation

- **Implemented:** task-role-only attachment support, plan-time identity checks, attachment-readiness ordering, and exact inventory checks in `validate-iam.sh`. Execution-role ECR/logging/GuardDuty authority remains separate.
- **Offline tested:** `scripts/tests/test-ecs-task-role-managed-policies.sh` passed **13/13** cases during the M4 local checkpoint and again in [Static Analysis run 39368786319](https://github.com/jcub-i0/terraform-secure-baseline/actions/runs/39368786319). Cases include empty/default inventory, exact attachments, unexpected or missing attachments, duplicates, wrong account/partition, wildcard and malformed policy ARNs.
- **Live observed:** a later M2 `dev` workload's `validate-iam.sh` passed the configured ECS task-role managed-policy attachment inventory and execution-role separation checks. That evidence establishes live inventory comparison, **not** effective policy permissions or application API behavior.

### M1 live-authorization acceptance criterion — explicitly deferred

**Maintainer decision (October 20, 2026):** Defer an additional live positive/negative AWS API exercise using a Terraform-managed ECS **application task role** for `v1.12.0`. The maintainer reports comparable authorization testing has been performed many times previously; those exercises have not been linked in this ledger to an exact M1 application-role policy, tested revision, and retained allowed/denied API responses. **The roadmap's live authorization criterion is not recorded as passed.** This is an explicit release-qualification exception rather than evidence of an executed M1 test.

**Basis for accepting the deferral:** M1's IAM role and attachment implementation is merged; 13/13 offline managed-policy inventory checks passed; and live IAM inventory validation checked attachment equality and task/execution-role separation during M2 qualification. These checks do **not** independently prove effective permissions inside a supplied policy or successful/denied application API requests.

**Scope of deferral:** No new reference image, customer-managed test policy, ECS service, or infrastructure deployment is required solely to repeat this live API exercise during M4. This decision does **not** waive existing Static Analysis, IAM validator, 16-script baseline, GuardDuty, or Terraform-plan controls.

**Revisit when:** the task-role authorization/attachment contract materially changes, or before relying on unqualified customer-managed application task policies in a customer onboarding or security sign-off. Record the policy ARN/document, request identity, explicitly allowed and denied actions/resources, actual API response/errors, task definition and image digest, environment/revision, and cleanup evidence at that time.

No application-specific policy content or access to a Bedrock model is implicitly approved by this milestone.

## 9. Qualification exclusions and deferrals

This record does **not** establish:

- `staging` or `prod` live M1–M3 integration; the M3 demonstration used two `dev` AZs, not a production three-AZ topology;
- production Network Firewall or `vpc_endpoints_only` connectivity for Bedrock;
- authenticated or authorized Bedrock `InvokeModel`/`Converse`, service-control-policy or resource-policy enforcement;
- a successful **live** M1 allowed/denied AWS API pair on a reference ECS application role;
- ALB ingress, ALB target health, WAF, TLS end-to-end application behavior, or ALB access logging in the M2/M3 `dev` exercise;
- continuous GuardDuty data reporting merely from sidecar injection;
- production RDS failover, AWS Backup restoration, data consistency, regional recovery, or retirement/teardown proof;
- a complete signed evidence chain, formal SOC 2/ISO 27001 certification, or unconditional security adequacy.

The roadmap expressly defers verified RDS recovery, AWS WAF, and ALB access logs to `v1.13.0`, with broader security/remediation and advanced runtime patterns kept outside `v1.12.0`.
