# Validation Evidence Guide

## Purpose

This guide explains how to interpret validation evidence generated by the `tf-secure-baseline` validation suite.

This guide does not assert that any particular deployment was tested. Use the actual run's tested commit, effective configuration, and retained evidence.

The suite provides repeatable, read-only checks across four layers:

- workload bootstrap
- workload baseline
- control plane
- security operations

Together, these layers help confirm that selected AWS security controls, Terraform state resources, GitHub OIDC resources, organization governance, centralized security-service configuration, and workload-local realization match the expected baseline design.

Read-only describes the intended AWS control-checking operations, not an absence of local writes or an IAM read-only permission set. Exporters create local reports; initialization and backend checks use local files and state access. A Plan role can have state-write and KMS/secret permissions. Do not run these tools with unreviewed credentials or treat their output as a least-privilege role certification.

The validation evidence can support:

- Deployment verification
- Internal security review
- Client handoff
- Troubleshooting
- Lightweight audit-readiness discussions
- Control implementation evidence

## Evidence Workflow

The recommended evidence sequence follows the architecture boundary:

1. Validate and export the control plane to confirm Organizations topology, delegated-administrator prerequisites, Identity Center, and control-plane state/OIDC foundations.
2. Validate and export security operations to confirm centralized Security Hub CSPM, GuardDuty, and Security Hub V2 governance.
3. For each workload account, validate and export workload bootstrap state/OIDC resources.
4. For each deployed workload account, validate and export the workload baseline.
5. Review the generated `summary.md` and `summary.json` files for all applicable layers.
6. Complete live or privileged tests that remain manual by design.
7. Document warnings, exceptions, evidence retention, and sign-off decisions.

Each report is intentionally scoped. For example, security-operations evidence validates centralized governance but does not replace control-plane topology evidence or workload-local validation.

### Execution context and Region authority

Run local examples from the repository root with initialized backends, an explicit expected account, and the intended credential chain. Replace the account/repository examples before running them. The example `us-east-1` is not a universal service or backend requirement.

| Entry point | Service Region behavior |
|---|---|
| Workload baseline validators and `export-baseline.sh` | Resolve `primary_region` from deployed workload outputs; a supplied `AWS_REGION`, including an empty value, must match |
| Bootstrap validator/exporter | Require explicit `AWS_REGION` for the account/service scope; state-bucket and state-KMS checks use separately resolved backend Region |
| Control-plane validator/exporter | Require explicit control-plane service `AWS_REGION`; do not infer it from a workload |
| Security-operations validator/exporter | Require explicit delegated-administrator service `AWS_REGION`; this report is scoped to `security_services` |
| `migrate-state-stack.sh` | A separate administrative operation, not an exporter; derives/checks the backend template Region |

State roots provision their bucket/CMK through `state_region`; S3 backend `region` is explicit backend configuration. Neither is a synonym for workload `primary_region`. A caller profile's default Region is not the workload validator's authority. Changing a variable does not migrate existing state or resources, and Region configurability is not evidence of multi-Region qualification.

Use the pinned Terraform `1.15.8` and each root's committed provider lockfile for RC1 work. Store configuration and version provenance with the report. Do not change or migrate infrastructure merely to make a read-only evidence collection pass.

### Naming Convention

Most environment-specific validation scripts derive resource names with this pattern:

```bash
ENV_NAME="${1:-}"
CLOUD_NAME="${CLOUD_NAME:-tf-secure-baseline}"
NAME_PREFIX="${NAME_PREFIX:-${CLOUD_NAME}-${ENV_NAME}}"
```

Use `CLOUD_NAME` for normal project/client naming customization. Use `NAME_PREFIX` only when validating resources that intentionally do not follow the default `${CLOUD_NAME}-${ENV_NAME}` naming convention.

### GitHub Evidence Workflows

The manual GitHub evidence workflows obtain OIDC credentials for the Plan role associated with the selected GitHub Environment. The checks are non-mutating workload inspections; the role itself is not restricted to read-only IAM permissions:

| Evidence Scope | GitHub Environment | Terraform roots initialized before export |
|---|---|---|
| Workload bootstrap | `<env>-plan` | `bootstrap/<env>/state`, `bootstrap/<env>/account`, and `environments/<env>` |
| Workload baseline | `<env>-plan` | `environments/<env>` |
| Control plane | `control-plane-plan` | `bootstrap/control_plane/state`, `account`, `organizations`, and `identity_center` |
| Security operations | `security-operations-plan` | `bootstrap/security_operations/security_services` |

The bootstrap and control-plane workflows use strict remote-state validation for release/client-facing evidence. Security-operations evidence validates the applied centralized-security stack and live AWS state from the delegated administrator account.

The workflows render the generated Markdown summary in the GitHub Actions run summary and upload the timestamped evidence directory as an artifact.

GitHub OIDC does not use a named AWS CLI profile. A workflow-generated report may therefore show:

```text
AWS Profile: not set
AWS Credential Source: GitHub OIDC environment credentials
```

This is expected in the configured OIDC workflows and does not indicate missing AWS credentials. The exporter derives this label from `AWS_PROFILE` and `GITHUB_ACTIONS`; the text is not independent proof that OIDC was actually used. Retain the credential-configuration step and caller identity from the run.

## Report Package Contents

Validation evidence is generated by layer.

### Workload Bootstrap Evidence Package

| File | Purpose |
|---|---|
| `summary.md` | Human-readable workload bootstrap validation report |
| `summary.json` | Machine-readable workload bootstrap validation summary |
| `validate-bootstrap.log` | Supporting workload bootstrap validation log |

### Workload Baseline Evidence Package

| File | Purpose |
|---|---|
| `summary.md` | Human-readable workload baseline validation report |
| `summary.json` | Machine-readable workload baseline validation summary |
| `validate-*.log` | Per-script workload baseline validation logs |

The current baseline suite uses `validate-security-workload.sh` and records its log as `validate-security-workload.log`.

### Control-Plane Evidence Package

| File | Purpose |
|---|---|
| `summary.md` | Human-readable control-plane validation report |
| `summary.json` | Machine-readable control-plane validation summary |
| `validate-control-plane.log` | Supporting control-plane validation log |

### Security-Operations Evidence Package

| File | Purpose |
|---|---|
| `summary.md` | Human-readable centralized-security validation report |
| `summary.json` | Machine-readable security-operations validation summary |
| `validate-security-operations.log` | Supporting security-operations validation log |

The Markdown summaries are intended for human review. The JSON summaries are intended for automation, artifact ingestion, evidence indexing, dashboards, or reporting pipelines. The per-script logs provide supporting detail for each validation area.

### What the summaries actually record

`export-baseline.sh` invokes all 16 top-level validators and records one PASS/FAIL result per script from its exit status. It continues collecting other script results after a child fails. It does not count every individual assertion, classify every warning in JSON, or prove that every conditional branch executed. Missing/non-executable child scripts fail. A prerequisite or identity failure before collection can leave no complete package; absence of a report is not PASS or not applicable.

The generated baseline JSON includes account/Region, naming, credential-source label, validation time, script counts, results, and a static `manual_validation_remaining` list. That list is guidance, not a live completion tracker or an exhaustive qualification ledger. The baseline summary does not automatically record a Git commit, deployment image digests, provider-lockfile hash, backend identity, or a signed evidence manifest. Other layer exporters have their own schemas; do not assume all four JSON layouts are identical.

Keep original generated summaries/logs unchanged. Put reviewer-supplied provenance and acceptance decisions in a companion record or the [report template](validation-report-template.md), not in invented exporter fields.

### Provenance required for release or client claims

| Evidence item | What to record separately where not generated |
|---|---|
| Implementation and validator identity | Actual checked-out commit, local modifications, and applicable source tag; distinguish the last deployed commit from the validator checkout |
| Effective deployment | Profile, service Region, VPC CIDR/AZs, canonical service registrations and selected digests, relevant overrides, normal versus retirement posture |
| Backend context | Target root, bucket/key/Region identity and workspace; no credentials or raw secret-bearing state in a public report |
| Toolchain | Actual Terraform/provider versions and root lockfile checksum |
| Caller and run | Caller ARN/account, credential configuration, workflow/run ID and attempt, operator/time and local execution context |
| Evidence integrity | Package location, retained original artifacts/logs, and separately generated checksums under the organization's evidence process |
| Behavioral exercise | Tested commit/configuration, triggering action, expected/observed result, recovery and cleanup evidence |

A no-change Terraform plan with the same effective inputs complements the live checks; `terraform output` alone reads stored outputs and is not a fresh plan. Record which configuration was actually deployed. Do not label an earlier R8 exercise or a later configuration-only regression as an exact-RC1 recovery test merely because the current documentation references RC1.

## What Automated Workload Bootstrap Validation Covers

Workload bootstrap validation is handled separately from workload baseline validation because bootstrap resources establish Terraform state storage, state encryption, backend locking behavior, and GitHub OIDC execution roles.

| Area | Coverage Summary |
|---|---|
| AWS Identity | Confirms the active AWS caller identity and optional expected workload account ID |
| Bootstrap Directories | Confirms `bootstrap/<env>/state`, `bootstrap/<env>/account`, and `environments/<env>` paths exist |
| State Stack Remote Backend | Optionally requires `bootstrap/<env>/state` to declare a readable S3 backend and confirms `terraform state pull` succeeds |
| Backend Files | Confirms state, account, and workload stacks define backend files after migration |
| S3 Native Locking | Confirms all three workload Terraform roots use `use_lockfile = true` |
| Backend State Configuration | Confirms state, account, and workload stacks use the same state bucket/region with distinct state object keys |
| Remote State Object | Confirms the state stack object exists in S3 and the backend bucket matches `tf_state_bucket_name` |
| State S3 Bucket | Confirms the state bucket exists, has versioning, public access block settings, and SSE-KMS encryption |
| State KMS CMK | Resolves the state CMK from live bucket encryption and confirms it is enabled and customer-managed |
| GitHub OIDC | Confirms the workload account GitHub OIDC provider exists |
| GitHub Plan/Apply Roles | Confirms workload GitHub plan/apply roles exist |
| GitHub Trust Conditions | Confirms Plan/Apply trust policies reference the expected GitHub repository and environment subjects |
| State Access Policies | Confirms GitHub roles reference the state bucket, state objects including `.tflock` objects, and the state CMK |
| Workload CMK Policy Access | Confirms the GitHub Apply role references current workload-created Lambda and Secrets Manager CMK ARNs |
| Image Publisher Role | When enabled or explicitly required, confirms the role exists in the active workload account and matches the Terraform output |
| Image Publisher Trust | Confirms one `Allow` trust statement for `sts:AssumeRoleWithWebIdentity`, the workload OIDC provider, `sts.amazonaws.com`, and the exact configured branch subjects |
| Image Publisher ECR Policy | Confirms the exact Terraform-defined ECR publication/query action set, one registry-wide `ecr:GetAuthorizationToken`, and repository-scoped access limited to `<name-prefix>-*` |
| Image Publisher Authority Boundary | Rejects unexpected state, ECS, IAM, deny, conditional, `NotAction`, `NotResource`, or general administrative authority |

### Image Publisher Validation Boundary

The Image Publisher role is a workload-bootstrap concern because it is created by `bootstrap/<env>/account`. When `image_publisher_role_github_arn` is present, `validate-bootstrap.sh` validates the role even if it is optional. For publisher-enabled release/client evidence, require it explicitly and provide the expected branch set:

```bash
REQUIRE_BOOTSTRAP_GITHUB_IMAGE_PUBLISHER_ROLE=true
EXPECTED_GITHUB_IMAGE_PUBLISHER_BRANCHES='["main"]'
```

Strict publisher validation also requires `EXPECTED_GITHUB_REPOSITORY` so the validator can construct and compare the exact branch-based OIDC subjects. The publisher trust uses branch subjects such as `repo:<owner>/<repo>:ref:refs/heads/main`; it is intentionally different from the environment subjects used by the Plan and Apply roles.

### Remote State Stack Evidence

`validate-bootstrap.sh`, `validate-control-plane.sh`, and their exporters use:

```bash
REQUIRE_STATE_STACK_REMOTE="${REQUIRE_STATE_STACK_REMOTE:-false}"
```

| Value | Evidence Meaning |
|---|---|
| `true` | A missing, mismatched, or unreadable state-stack S3 backend fails validation. Use this for release-readiness and client-facing evidence. |
| `false` | The optional remote-state proof path can report migration findings as warnings. This does not relax every mandatory directory, account, backend, or AWS check. Use only for documented transition/troubleshooting. |

The GitHub bootstrap and control-plane evidence workflows default this input to `true`. On clean runners, the workflows also initialize the state-stack backend before running the exporter.

The checks provide evidence that the configured state backend is not merely declared: the expected S3 object must be readable, the key must not collide with another Terraform root, and `terraform state pull` must succeed.

The validators do not perform migration. Existing deployments must complete `terraform init -migrate-state` separately before strict evidence is collected.

### Strict Workload CMK Policy Evidence

`validate-bootstrap.sh` and `export-bootstrap.sh` use `STRICT_WORKLOAD_CMK_POLICY_CHECKS`.

Default behavior:

```bash
STRICT_WORKLOAD_CMK_POLICY_CHECKS="${STRICT_WORKLOAD_CMK_POLICY_CHECKS:-true}"
```

| Value | Evidence Meaning |
|---|---|
| `true` | Stale or missing workload Lambda / Secrets Manager CMK policy references fail validation. This is the default and is recommended for client-readiness evidence. |
| `false` | Stale or missing workload CMK policy references are reported as warnings. The checks still run; they become advisory rather than skipped. |

Strict workload CMK evidence indicates that `bootstrap/<env>/account` has been reconciled with the current workload-created CMK outputs from `environments/<env>`:

```text
lambda_cmk_arn
secrets_manager_cmk_arn
```

Set `STRICT_WORKLOAD_CMK_POLICY_CHECKS=false` only for transitional runs, early/manual GitHub workflow testing, or environments where the workload stack has not yet been reconciled back into `bootstrap/<env>/account`.

## What Automated Workload Baseline Validation Covers

The automated workload baseline suite runs 16 read-only validators covering environment identity, networking, VPC endpoints, ECR, logging, workload security, KMS, Backup, SNS, SQS, EventBridge, Lambda, SSM, EC2 compute, ECS runtime, and IAM.

The evidence contract includes the ECS runtime/security checks and exact topology, production-availability, RDS resilience, and Restore Testing configuration checks within the same 16-script suite.

`validate-ecs-runtime.sh` verifies:

- deployment-profile Runtime Monitoring intent (`production`/`development` enabled; `minimal` disabled);
- exact Terraform and live `GuardDutyManaged=true|false` cluster intent;
- exact Container Insights setting and performance-log identity/retention/KMS encryption;
- exact live service inventory and service steady state;
- application-only Terraform task definitions;
- Fargate platform compatibility;
- digest-pinned application images and exact logging/network relationships;
- one running GuardDuty agent per protected running task while the application container remains valid;
- GuardDuty ECS coverage management type, health, and issues;
- fixed-versus-autoscaled desired-count ownership;
- exact Application Auto Scaling targets and target-tracking policies;
- deployment-health configuration; and
- Terraform-owned task-deficit and ingress unhealthy-target alarms.

Live GuardDuty agent names are not assumed to be a single literal value. The validator accepts `aws-gd-agent` or an AWS-generated name beginning `aws-guardduty-agent-`, while still requiring exactly one injected agent and `lastStatus = RUNNING`.

For protected `production` and `development` clusters with running tasks, GuardDuty coverage must identify the expected ECS cluster and report:

```text
Fargate ManagementType = AUTO_MANAGED
CoverageStatus          = HEALTHY
Fargate Issues          = []
top-level Issue          = empty
```

For `minimal`, healthy coverage is not required. A missing coverage record is valid; if a matching record exists, Fargate `ManagementType` must be `DISABLED`.

With no deployable ECS services, live coverage is not required; with no running protected tasks, protected HEALTHY coverage is not required until tasks run. Record how many services/tasks were actually checked. RC1's tracked sample digests are null, so baseline-only qualification can legitimately omit task/ALB instrumentation checks.

Supporting workload validators provide the rest of the Runtime Monitoring evidence chain:

- `validate-vpc-endpoints.sh` requires the full live Interface Endpoint map to exactly match Terraform and requires exactly one Terraform-owned `guardduty-data` endpoint;
- `validate-iam.sh` requires the exact regional GuardDuty-agent ECR image-pull scope when protected, no GuardDuty-agent scope for `minimal`, and no broad/unexpected ECR authority;
- `validate-eventbridge.sh` requires the exact healthy/unhealthy GuardDuty ECS coverage rule, the existing SecOps SNS target, shared EventBridge DLQ, three retries, 3600-second maximum event age, and required input-transformer fields; and
- `validate-security-workload.sh` verifies workload GuardDuty detector health and the centralized administrator relationship.

AWS Backup evidence is also profile-aware. `validate-backup.sh` treats the encrypted environment backup vault as retained in both enabled and disabled states. When scheduled backup is disabled, effective schedule/retention resolve to null, the plan/selection must be absent, and workload EC2/RDS resources must use `Backup=false`. When enabled, schedule, retention, plan, selection, and `Backup=true` resource tags must match Terraform exactly.

### Topology and availability evidence

`validate-networking.sh` checks Terraform-derived VPC/subnet identity and CIDRs, seven subnet families, AZ associations, mode-specific routes, ingress/egress separation, and same-AZ NAT/firewall relationships. Production defaults to three AZs; development/minimal to two. The baseline accepts a canonical `/16` and derives `/24` families, but a successful default-CIDR run is not a non-default-CIDR portability test.

The ECS runtime validator checks normal-production capacity and deployment policy: at least two fixed tasks or a scaling minimum of two, enabled AZ rebalancing, minimum healthy percent `100`, and maximum percent at least `200`. Exact live placement of one task in each of three AZs is a separate observation, not implied by a subnet count or rebalancing flag. A steady-state check is not the same exercise as stopping a task and observing replacement.

### RDS configuration versus deletion-time intent

`validate-backup.sh` compares live RDS identity, Multi-AZ, DB subnet-group name, VPC security-group set, deletion protection, backup retention, public accessibility, and storage encryption with the resource-backed output. It checks final-snapshot and automated-backup deletion intent against Terraform state. Those deletion-time flags are not evidence that a final snapshot already exists.

The check is not an exhaustive RDS configuration audit: it does not compare engine/version, instance class, all storage/parameter settings, or exact member-subnet membership merely because related metadata is available elsewhere. It does not run SQL, force failover, or prove application recovery. The source is an RDS DB instance, not Aurora or a Multi-AZ DB cluster; three data AZs do not establish three database servers.

### Restore Testing configuration, execution, validation, and cleanup

Production with effective AWS Backup enabled configures the RDS Restore Testing plan/selection. The live configuration check covers the exact source RDS ARN, vault-selection contract, schedule/windows, Backup role, and private restore metadata. The temporary restored database is configured Single-AZ even though the source production database is Multi-AZ.

The validator then reports the latest job returned for the configured plan. Its handling is deliberately not a single “recovery passed” result:

| Observed state | Current script treatment | Acceptance implication |
|---|---|---|
| No Restore Testing job | Warning; configuration can pass | No live restore execution proved |
| Restore `PENDING` / `RUNNING` | Warning | Execution incomplete |
| Restore `COMPLETED` | Pass message for execution | Not by itself application validation or cleanup proof |
| Restore `FAILED` / `ABORTED` | Failure | Investigate failed execution |
| Application validation `FAILED` / `TIMED_OUT` | Warning | Do not claim successful application validation |
| Application validation `VALIDATING` | Warning | Validation incomplete |
| Application validation `SUCCESSFUL` | Reported success | Retain what validation actually did; the baseline does not implement application validation logic |
| Cleanup/deletion `FAILED` or `DELETING` | Warning | Cleanup unresolved or incomplete |
| Cleanup/deletion `SUCCESSFUL` | Reported success | Retain the job/resource cleanup evidence |

A script PASS can coexist with missing jobs or unresolved validation/cleanup warnings. Review the complete `validate-backup.log`, job ID, recovery-point ARN, created resource ARN, timestamps, and all three status dimensions before accepting recovery evidence. The latest job alone is not a full historical reliability record. Earlier restore qualification must retain its own source/configuration provenance.

Operational alarm state remains deliberate: `OK` passes, `INSUFFICIENT_DATA` is a warning that metric evaluation is not yet complete, and `ALARM` fails runtime validation.

The earlier v1.10 R6 development qualification is historical Runtime Monitoring evidence, not a new v1.11 execution claim. Generated summaries/logs plus retained run provenance remain the record for each individual evidence run.
## What Automated Control-Plane Validation Covers

Control-plane validation establishes the organization and access foundation that centralized security depends on.

Coverage includes:

- control-plane AWS identity and Terraform root structure
- control-plane state backend, native S3 locking, and optional strict remote-state proof
- state bucket and state CMK protections
- control-plane GitHub OIDC provider and Plan/Apply roles
- AWS Organizations ALL-features mode
- `Workloads`, `NonProd`, `Prod`, and root-level `Security` OU topology
- active `dev`, `staging`, `prod`, and `security-operations` account identity
- strict workload and security-operations account placement when `STRICT_ACCOUNT_OU_CHECKS=true`
- Security Hub and GuardDuty trusted service access and delegated-administrator registration
- Security Hub V2 `SECURITYHUB_POLICY` organization prerequisite
- IAM Identity Center instance, required groups, permission sets, and assignments

Current control-plane validation defaults `STRICT_ACCOUNT_OU_CHECKS=true` and `STRICT_IDENTITY_CENTER_ASSIGNMENTS=true`. A run that deliberately disables either setting should be identified as weaker evidence because mismatches become advisory instead of blocking.

## What Automated Security-Operations Validation Covers

Security-operations validation confirms centralized security governance from the delegated administrator account.

Coverage includes:

- security-operations AWS caller identity;
- `bootstrap/security_operations/security_services` Terraform outputs and applied state;
- Security Hub and GuardDuty trusted-access / delegated-administrator dependencies;
- GuardDuty malware-protection trusted access where required;
- Security Hub V2 `SECURITYHUB_POLICY` enablement prerequisite;
- Security Hub CSPM administrator state and finding aggregation;
- Security Hub CSPM `CENTRAL` organization configuration;
- CSPM configuration policies and workload account associations;
- GuardDuty administrator detector and organization member enrollment;
- the exact Terraform-managed GuardDuty organization feature subset;
- verification that AWS-returned organization features outside Terraform management remain disabled;
- Security Hub V2 administrator state;
- Security Hub V2 organization policy attachment to `Workloads`; and
- effective Security Hub V2 policy for configured workload accounts.

The GuardDuty Runtime Monitoring organization contract is:

```text
RUNTIME_MONITORING           = ALL
ECS_FARGATE_AGENT_MANAGEMENT = ALL
EC2_AGENT_MANAGEMENT         = ALL
EKS_ADDON_MANAGEMENT         = NONE
```

AWS can return supported GuardDuty organization features that are not present in Terraform's managed feature map. That is not itself drift. The validator requires the Terraform-managed subset to match exactly and separately requires every unmanaged returned feature and its additional configurations to remain `NONE`.

This layer intentionally does not prove the complete AWS Organizations topology; that belongs to control-plane validation. It also does not prove workload-local Runtime Monitoring realization, Config, Inspector, Backup, networking, compute, or remediation state; those belong to workload validation.
## Application Release Evidence

`Deploy Application` produces a technical chain that can supplement workload infrastructure evidence. Useful artifacts include publication metadata, the authoritative ECR digest re-check, workflow run identity, the generated release branch/PR, and the one-field `image_digest` change. The workflow does not manage `scaling`, `deployment`, GuardDuty organization policy, or the GuardDuty runtime agent.

For publisher-enabled workloads, strict bootstrap evidence can separately prove the Image Publisher role's exact branch trust, ECR action set, repository scope, and authority boundary.

After the release PR is merged, collect the separate `Terraform Apply` run showing the internal saved plan, checksum/metadata verification, protected approval, and exact-plan apply. Follow that with ECS convergence and the workload baseline evidence package. For autoscaled services, runtime validation evaluates the live desired count against the Terraform min/max scaling bounds rather than requiring Terraform's bootstrap count to be reasserted. Do not treat successful image publication by itself as proof that the application was deployed. For a protected `production` or `development` cluster, the post-apply workload evidence should also prove the injected GuardDuty agent and healthy `AUTO_MANAGED` ECS coverage. Terraform's canonical task definition remains application-only; GuardDuty service-manages the live agent.

The publisher job and release/PR job intentionally hold different authorities: AWS OIDC/ECR publication versus GitHub repository mutation. Preserving that evidence helps demonstrate the intended separation of duties.

For the credential-helper hardening, capture an actual post-change publishing run. The implementation uses a temporary push-only Docker configuration and disables helper token-file caching; it does not prove old credential files were removed, nor that no credential existed in memory. The ECS runtime validator cannot inspect a past runner's filesystem.

## Production retirement evidence

Retirement is outside the normal-state 16-validator workload acceptance contract. Its deployment scripts provide separate checks and mutations; they do not add another evidence layer. Retain evidence for each boundary:

| Boundary | Evidence and limit |
|---|---|
| Stage-1 preparation | Exact saved plan, `validate-production-retirement-plan.sh` result, protected Apply; the guard rejects create/delete/replacement but is not an attribute-level allowlist |
| Durable-data decision | Preflight inventory, explicit `delete_durable_retirement_data=true`, and cleanup approval; the cleanup helper is `prod`-only and authorization is required even for empty scoped data |
| Durable cleanup | `cleanup-retirement-durable-data.sh --mode apply` run and post-cleanup inventory; it re-inventories rather than applying a frozen item manifest |
| Live readiness | `validate-retirement-readiness.sh`: live native protections, zero ECS desired/running/pending counts and scaling bounds, empty scoped ECR/vault and no active Backup jobs, plus RDS deletion-time intent |
| Identity Center | Separate cleanup plan and protected control-plane apply before final workload-destroy approval; persistent configuration reconciliation is separate |
| Destroy | Saved workload destroy plan, metadata/checksum verification, final approval, readiness recheck, and exact saved-plan apply |
| Retained recovery/evidence assets | Final RDS snapshot, retained automated backups and any externally preserved evidence must be verified after the operation; a successful plan does not prove preservation |

Rejecting a later approval does not undo earlier durable deletion or Identity Center changes. Required reviewer configuration must be checked independently of workflow YAML. This is not a full-platform/account/state decommissioning qualification. Follow the [retirement runbook](../production-retirement.md), including abort and retained-data handling.

## What Automated Validation Does Not Cover

The validation suite is intentionally read-only and layer-specific. A check omitted from one report may still be automated by another evidence workflow.

Additional behavioral evidence includes controlled ECS replacement, actual RDS failover and recovery, Restore Testing execution/application validation/cleanup, and retirement/destroy execution. Automated retirement-plan/readiness gates exist, but reading their code or running a normal workload exporter does not execute the lifecycle. Perform only the specifically authorized exercises; do not rerun destructive tests merely to populate a template.

Across a full evidence set, the following activities still require live, privileged, destructive, or human review rather than these read-only validators:

- IAM Identity Center end-user login and effective-access testing
- live EC2 isolation execution
- live EC2 rollback execution
- live IP enrichment execution
- tamper-detection simulation
- break-glass role assumption
- destroy-safety review and approved teardown execution
- policy and procedure review
- control-owner review
- formal audit evidence evaluation

GitHub Actions evidence workflow execution itself is observable through the workflow run and uploaded artifact; it is separate from the AWS-state assertions inside the generated report.

## Interpreting PASS, WARN, and FAIL

### PASS

A per-check `[PASS]` message records that particular assertion. An exporter script-level `PASS` means the child exited successfully; it can include non-blocking warnings and inapplicable/skipped branches. `16/16` therefore means 16 successful script exits, not every control proven, zero warnings, application acceptance, or achieved recovery objectives.

A passing result should be interpreted in the context of the selected deployment profile, effective Terraform outputs, and whether the check applies to workload infrastructure or control-plane governance resources.

For example, a development environment may pass with scheduled AWS Backup disabled when `effective_backup_enabled=false`, provided the encrypted backup vault remains present, effective schedule/retention are null, the plan/selection are absent, and workload EC2/RDS resources use `Backup=false` as required by `validate-backup.sh`.

A control-plane validation run may still contain non-blocking warnings for optional checks. Required account OU placement is strict by default; it becomes advisory only if `STRICT_ACCOUNT_OU_CHECKS=false` is deliberately used for a transitional run.

### WARN

A `WARN` message indicates something that may require review but does not necessarily mean the environment is invalid.

Warnings may be expected in some environments.

Examples include:

- Optional resources not present
- Pending SNS email confirmation
- No custom patch baseline configured
- Detailed Backup checks delegated from `validate-security-workload.sh` to `validate-backup.sh` when scheduled backup is disabled
- Network Firewall absent because the environment uses `nat_only`
- NAT Gateway absent because the environment uses `vpc_endpoints_only`
- An ECS operational alarm in `INSUFFICIENT_DATA` while the metric has not yet accumulated enough datapoints
- State-stack migration findings when `REQUIRE_STATE_STACK_REMOTE=false` was intentionally selected
- Image Publisher role absence when application publication is intentionally disabled and `REQUIRE_BOOTSTRAP_GITHUB_IMAGE_PUBLISHER_ROLE=false`

Warnings should be reviewed before client handoff or sign-off.

In particular, no Restore Testing jobs, incomplete restore execution, failed/timed-out application validation, or unresolved temporary-resource cleanup cannot be silently converted into successful recovery evidence. Separate the automated verdict from the reviewer's acceptance decision.

### FAIL

A `FAIL` result means a required validation check did not pass.

Failures should be reviewed before relying on the environment or control plane as validated evidence.

A failed validation script may indicate:

- Missing Terraform outputs
- Missing AWS resources
- Incorrect account or region
- Incorrect `CLOUD_NAME` or `NAME_PREFIX`
- Missing current workload CMK policy references in the GitHub Apply role when strict workload CMK checks are enabled
- Missing, colliding, or unreadable state-stack S3 backend when `REQUIRE_STATE_STACK_REMOTE=true`
- Incorrect deployment profile assumptions
- Incorrect control-plane account profile
- Incorrect expected GitHub repository value
- IAM trust policy issues
- Image Publisher trust or ECR publication policy differing from the Terraform-defined contract when the role is enabled or required
- ECS autoscaling target/policy inventory, deployment-health settings, or Terraform-owned operational alarms differing from Terraform outputs
- A Terraform-owned ECS operational alarm currently in `ALARM`
- `GuardDutyManaged` differing from the deployment-profile/Terraform contract
- a protected running task missing its GuardDuty agent or reporting the agent as non-`RUNNING`
- protected GuardDuty ECS coverage not `AUTO_MANAGED` / `HEALTHY`, or reporting unresolved issues
- duplicate or non-Terraform `guardduty-data` endpoint identity
- GuardDuty agent ECR authority missing, present for `minimal`, or broader than Terraform
- GuardDuty coverage EventBridge rule/target/DLQ/retry/transformer drift
- retained backup vault missing, an unexpected backup plan while disabled, or resource `Backup` tags differing from effective enablement
- Failed AWS CLI calls
- Missing required local tooling
- Mismatched resource naming
- Incomplete deployment

## Control-Plane Strictness and Warning Behavior

The current control-plane validator treats required account placement and Identity Center assignments as strict by default:

```text
STRICT_ACCOUNT_OU_CHECKS=true
STRICT_IDENTITY_CENTER_ASSIGNMENTS=true
```

Under the default settings, incorrect placement of `dev`, `staging`, `prod`, or `security-operations` in the expected OU hierarchy is a validation failure rather than a normal warning.

Warnings remain appropriate for optional or intentionally relaxed checks, such as optional Analyst/Engineer groups or a run that explicitly sets one of the strictness flags to `false`. If strictness is relaxed for transitional troubleshooting, document that fact in the evidence package or handoff because the resulting evidence is weaker than the default release posture.

## Compliance Positioning

The validation suite can support audit-readiness and control implementation discussions, but it should not be represented as a certification or audit opinion.

The validation suite confirms the presence and configuration of selected AWS security controls, governance resources, and supporting infrastructure at the time validation was performed.

The validation suite does not replace:

- A full compliance program
- A SOC 2 audit
- An ISO 27001 audit
- Internal control design review
- Control operating effectiveness testing
- Formal audit evidence review
- Policy and procedure documentation
- Risk assessment
- ISMS implementation
- Management review
- Vendor risk management
- Legal or regulatory review

Recommended positioning:

- “This report provides deployment validation evidence.”
- “This report supports audit-readiness efforts.”
- “This report confirms selected AWS security controls were present and configured at the time of validation.”
- “This report should be reviewed alongside policies, procedures, risk assessments, and other compliance evidence.”

Avoid positioning such as:

- “This environment is SOC 2 compliant.”
- “This environment is ISO 27001 certified.”
- “This report proves compliance.”
- “This report replaces an audit.”
- “This report proves operating effectiveness.”

## Evidence Retention

Validation evidence should be retained according to the organization’s evidence retention expectations.

The Baseline Evidence workflow requests 30-day artifact retention; the exact-plan Apply/Destroy artifacts request one day. These are workflow retention settings, not an organizational archive or evidence-preservation guarantee. Preserve required records before expiry under the approved process. A checksum supplied and retained by the reviewer helps detect subsequent byte changes but is not an independent signature or proof of execution.

Recommended retention considerations:

| Evidence Type | Recommended Handling |
|---|---|
| Workload bootstrap `summary.md` | Retain with deployment or client handoff records |
| Workload bootstrap `summary.json` | Retain for automation, indexing, dashboarding, or evidence package generation |
| `validate-bootstrap.log` | Retain as supporting bootstrap technical evidence |
| Workload baseline `summary.md` | Retain with deployment or client handoff records |
| Workload baseline `summary.json` | Retain for automation, indexing, dashboarding, or evidence package generation |
| Per-script workload baseline logs | Retain as supporting technical evidence |
| Control-plane `summary.md` | Retain with governance/control-plane evidence |
| Control-plane `summary.json` | Retain for automation, indexing, dashboarding, or evidence package generation |
| `validate-control-plane.log` | Retain as supporting control-plane technical evidence |
| Security-operations `summary.md` | Retain with centralized-security governance evidence |
| Security-operations `summary.json` | Retain for automation, indexing, dashboarding, or evidence package generation |
| `validate-security-operations.log` | Retain as supporting centralized-security technical evidence |
| Manual validation notes | Retain with sign-off or engagement records |
| Exceptions | Retain with risk acceptance or remediation tracking |

Generated evidence may contain:

- AWS account IDs
- AWS regions
- Resource names
- ARNs
- Environment names
- Validation timestamps
- Operational configuration details
- GitHub organization or repository names
- IAM Identity Center group and permission set names

Treat validation evidence as internal or client-confidential unless explicitly approved for public release.

## Recommended Internal Review Process

Before using validation evidence for client delivery or internal sign-off:

1. Confirm the correct AWS account and region were validated.
2. Confirm the correct workload environment was validated.
3. Confirm `EXPECTED_ACCOUNT_ID` matched the active AWS caller identity.
4. Confirm `CLOUD_NAME` and the derived `NAME_PREFIX` match deployed workload resource names.
5. Confirm workload bootstrap evidence was exported with `export-bootstrap.sh`, when applicable.
6. Confirm workload baseline evidence was exported with `export-baseline.sh`, when applicable.
7. Confirm control-plane validation/evidence export was run with the control-plane profile, when applicable.
8. Confirm security-operations validation/evidence export was run from the delegated administrator account, when applicable.
9. Confirm `EXPECTED_GITHUB_REPOSITORY` matched the repository trusted by the GitHub OIDC roles.
10. Confirm `STRICT_WORKLOAD_CMK_POLICY_CHECKS=true` unless advisory behavior was intentionally documented.
11. Confirm `REQUIRE_STATE_STACK_REMOTE=true` for bootstrap and control-plane release or client-facing evidence.
12. For publisher-enabled workloads, confirm `REQUIRE_BOOTSTRAP_GITHUB_IMAGE_PUBLISHER_ROLE=true` and `EXPECTED_GITHUB_IMAGE_PUBLISHER_BRANCHES` matches the approved branch set.
13. When ECS runtime security is in scope, review `validate-ecs-runtime.log` together with `validate-iam.log`, `validate-vpc-endpoints.log`, and `validate-eventbridge.log` so cluster intent, live agent/coverage state, exact ECR authority, endpoint ownership, and coverage notification routing are all represented.
14. Review `validate-backup.log` for the exact enabled/disabled Backup contract rather than inferring Backup state from the broader workload-security summary.
15. Confirm workflow-generated reports identify `GitHub OIDC environment credentials` when `AWS_PROFILE` is not set.
16. Review all failed checks.
17. Review all warnings.
18. Confirm live/manual validation items are tracked.
19. Confirm exceptions are documented.
20. Confirm evidence files are stored in the appropriate location.
21. Confirm generated evidence is not committed to the source repository.

22. Record checked-out versus deployed commit, actual toolchain/lockfile, effective topology/profile, service count and selected digests; distinguish RC defaults from test overrides.
23. Review RDS live configuration separately from Terraform deletion-time intent and Restore Testing's execution, validation, and cleanup statuses.
24. Preserve separate behavioral and retirement records, including earlier-run provenance, rather than relying on the exporter's static remaining-work list.
25. Verify the role actually used and the workflow approval settings; do not infer least privilege or human approval from labels alone.

This guide explains how to interpret validation evidence generated by the `tf-secure-baseline` validation suite.

It does not define a complete compliance program, risk management process, audit methodology, or operating model.
