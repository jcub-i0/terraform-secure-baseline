# v1.14.0 M3 — Production Operational Qualification

**Status:** `Complete` — maintainer-accepted M3 closeout on November 5, 2026, following verified staging production-profile deployment, SQL checks, core resilience experiments, and protected Terraform-managed retirement. Some originally scoped checks and independent post-destroy audits were **not** performed or reverified; their limitations and follow-ups are documented below, not recast as successful tests.

**Tested target:** Disposable `environments/staging` workload in `us-east-1` using `deployment_profile=production`; **not** the `prod` account. The workload was deployed, qualified and retired on November 5, 2026. The repository's staging registration was subsequently reset to `image_digest = null` during M4-A.

**Goal:** Establish measured, application-aware availability and recovery evidence for the existing baseline, identify material platform-owned defects, and safely retire the workload. This is not a production go-live certificate or a generic application benchmark.

## Qualification boundaries and baseline contract

- The production profile defaults to three Availability Zones, Network Firewall egress, Multi-AZ RDS **DB instance**, AWS Backup, scheduled RDS restore testing, and 90-day CloudWatch Logs retention. Confirm the *effective* Plan and live resources instead of treating defaults as deployed evidence.
- RDS is PostgreSQL 17.10 and currently uses the configured instance class (`rds_instance_class`, default `db.t4g.micro`), private subnets, 50 GiB gp3, 14-day native backup retention, and final-snapshot-on-production-retirement behavior.
- ECS provides circuit-breaker rollback, AZ rebalancing in production, configured container-native health where opted in, and ALB health for ingress services. Terraform has task-deficit and ALB-unhealthy-target alarms. Their **real detection timing and delivery** require live checks.
- AWS Backup has a default daily backup schedule and a **weekly** restore-testing schedule. The optional `restore_validation` Lambda/SQL workflow is **disabled unless explicitly enabled** and supplied with its own validation secret. Scheduled resource restoration alone does not prove application reconnect or SQL integrity.
- `waf_enabled` is an explicit opt-in (default `false`); do not claim WAF protection because the deployment profile is production.
- During M3-B, a disposable PostgreSQL canary image was published and promoted by immutable digest through the existing release PR and protected Apply path. The image and ECR repository were later removed in M3-D. After M4-A, the tracked staging service has `image_digest = null`, retains its generic ingress/capacity configuration and has no M3-specific secret or hostname references.
- M2's Terraform Destroy succeeded (296 Terraform-managed resources removed). The maintainer reports no workload infrastructure deployed as M3 begins. An independent review of any retained ECR, Backup, manual RDS snapshots, logs, KMS keys, and charges remains open under M2; it is **not** an additional M3-A approval gate. Do not equate an empty active workload with guaranteed absence of durable assets.
- Production retirement has its own protected sequence and must **never** be bypassed by switching the applied profile to `development` or `minimal`. Follow [Production Retirement](../production-retirement.md).

## Gate C — Controlled operational experiments (executed with documented limits)

The table below preserves the approved test methods; observed results and deviations follow it. The sole maintainer operated the tests and reported the results, with AWS run links where available. Raw local and AWS CLI outputs were not committed publicly.

| Experiment | Method / evidence | Exit criterion |
|---|---|---|
| Availability and placement | Capture real task IDs, AZs, desired/running counts, ALB target status, HTTPS success/errors, and SQL canary | Approved availability/placement criteria met, or documented gap |
| Task replacement | With stable baseline, deliberately stop **one** synthetic ECS task; observe replacement, ALB target behavior, task-deficit and unhealthy-target alarm transitions, and SecOps receipt | Healthy capacity converges; observed interruption and alarm latency recorded |
| Failed application rollout | Reuse M2's bounded release-acceptance procedure under the production profile, with a reviewed bad synthetic digest and a known healthy fallback | Apply gate refuses false acceptance; rollback/healthy restoration independently observed |
| RDS Multi-AZ failover | After seeding a committed canary and recording initial DB state, use a separately authorized RDS DB-instance **reboot with failover**; continuously observe SQL read/write recovery, client reconnect, RDS events, DNS behavior, and committed-row checksum | No lost **committed** canary rows; measured outage/reconnect within approved bounds or reported as a gap |
| Database backup restore | Confirm a completed, eligible recovery point and an approved **isolated** manual/restore-testing target. Restore without modifying source RDS, check seed row/checksum, demonstrate approved app/client reconnection path, measure elapsed duration, and delete/retain the temporary instance by disposition | Verified recoverable SQL canary with an independently measured restore duration; no remaining unapproved restore instances |
| Detection and notification | Inspect CloudWatch alarm coverage for ECS/ALB, RDS health/capacity, backup/restore failures, and relevant event subscriptions. Exercise real signals where safe; verify actual SNS delivery to the authorized SecOps recipient | Alert condition, alarm transition, delivered message, receipt timestamp, and cleanup documented; gaps become targeted M3 remediation |
| Evidence retention | Store sanitized test results outside the disposable workload; verify selected archive objects, checksums, KMS decrypt rights, retention decision, and retrieval after workload teardown | Required evidence remains readable independently of the retired environment |

For the current `aws_db_instance` Multi-AZ configuration, AWS documents an authorized `reboot-db-instance --force-failover` path. Do not confuse this with the different Multi-AZ **DB cluster** failover API. This operation interrupts database connections; deliberately initiate it only for the disposable staging test after verifying the intended RDS instance and that interruption is acceptable. See [AWS RDS failover](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html) and [RDS reboot](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RebootInstance.html).

The weekly AWS Backup restore-testing schedule may not execute during a short-lived staging window. A configured schedule is **not** evidence of a completed recovery. Choose a separate authorized restore test or a documented test window with a real recovery point. See [AWS Backup restore testing](https://docs.aws.amazon.com/aws-backup/latest/devguide/restore-testing.html).

**Monitoring-review candidates, not preapproved code changes:** RDS capacity and connection health, important RDS events/failover, AWS Backup job failures and restore-validation failure, app-level SQL health, and prolonged ALB 5xx/availability anomalies. Confirm current ownership, signal quality, thresholds, alarm cost/noise and integration before adding any baseline alarm. Retain 16 existing top-level validators; extend focused checks rather than creating another validator uncritically.
