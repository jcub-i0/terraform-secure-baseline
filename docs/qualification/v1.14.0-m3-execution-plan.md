# v1.14.0 M3 — Production Operational Qualification

**Status:** In progress — pre-deployment design only. No AWS deployment, spend authorization, fault injection, or data deletion is implied by this document.

**Target:** Disposable `environments/staging` workload with the **applied** `deployment_profile=production` in `us-east-1`. Never use the `prod` account for this qualification.

**Goal:** Establish measured, application-aware availability and recovery evidence for the existing baseline, identify material platform-owned defects, and safely retire the workload. This is not a production go-live certificate or a generic application benchmark.

## Qualification boundaries and existing facts

- The production profile defaults to three Availability Zones, Network Firewall egress, Multi-AZ RDS **DB instance**, AWS Backup, scheduled RDS restore testing, and 90-day CloudWatch Logs retention. Confirm the *effective* Plan and live resources instead of treating defaults as deployed evidence.
- RDS is PostgreSQL 17.10 and currently uses the configured instance class (`rds_instance_class`, default `db.t4g.micro`), private subnets, 50 GiB gp3, 14-day native backup retention, and final-snapshot-on-production-retirement behavior.
- ECS provides circuit-breaker rollback, AZ rebalancing in production, configured container-native health where opted in, and ALB health for ingress services. Terraform has task-deficit and ALB-unhealthy-target alarms. Their **real detection timing and delivery** require live checks.
- AWS Backup has a default daily backup schedule and a **weekly** restore-testing schedule. The optional `restore_validation` Lambda/SQL workflow is **disabled unless explicitly enabled** and supplied with its own validation secret. Scheduled resource restoration alone does not prove application reconnect or SQL integrity.
- `waf_enabled` is an explicit opt-in (default `false`); do not claim WAF protection because the deployment profile is production.
- The tracked `environments/staging/container-workloads.auto.tfvars.json` still references the M2 synthetic `test` digest. After M2 teardown the referenced ECR image may no longer exist; prepare a verified M3 image and fresh release digest before an application Apply.
- M2's Terraform Destroy succeeded (296 Terraform-managed resources removed), but independent audit of residual ECR, Backup, manual RDS snapshots, independently archived logs, KMS key usability, and costs is still pending. Start this audit before authorizing M3 spend.
- Production retirement has its own protected sequence and must **never** be bypassed by switching the applied profile to `development` or `minimal`. Follow [Production Retirement](../production-retirement.md).

| M2 residual audit | AWS-side inventory of tagged or named leftover artifacts, snapshot and recovery-point disposition, cost inventory, and evidence of any intentional retention | **Pending** |
| Environment inputs | `staging-plan` and `staging` GitHub environment variables/secrets agree on identity, `DEPLOYMENT_PROFILE=production`, ingress, TLS, region, retirement flag, SecOps recipients, and image-release inputs | **Pending** |
| Protection | Confirm real GitHub Environment reviewers/branch restrictions, required roles, non-public RDS, narrow approved ALB ingress CIDRs, valid ACM certificate, KMS access, and backup/restore prerequisites | **Pending** |
| Test data | Synthetic-only canary schema, authorized injection, least-privileged application DB role/secret (not master credentials embedded in code or logs), and evidence redaction | **Pending** |
| Evidence and retirement | Approved independent archive and retention interval for audit logs and results; S3 version/KMS decrypt verification plan; final-snapshot and backup-recovery-point disposition; production retirement authorization path | **Pending** |
| Acceptance thresholds | Owner-approved limits for application downtime, RDS client reconnect time, backup restore duration, alarm delivery time, capacity/recovery behavior, and allowed data loss | **Pending** |

AWS Budgets alerts and estimated pricing are not immediate hard spending caps. Keep a human-owned stop/retirement procedure, especially for RDS, firewall endpoints, retained snapshots, and backup recovery points.

**No-go triggers:** Wrong account/profile; unreviewed network exposure; unconfirmed SecOps delivery destination; unknown backup/key disposition; no agreed budget/stop owner; outdated image; an unexpected replacement or privilege escalation in the reviewed saved Plan; or unresolved safety issues in the retirement flow.

## Gate B — Synthetic application and reviewed deployment

1. Build a **disposable test fixture**, not private business logic or a permanent platform dependency. Use one container, digest-pinned ECR image, restricted HTTPS ingress, and the existing `Deploy Application` → release PR → protected Terraform Apply path.
2. Fixture behavior: `GET /health` (liveness without DB dependency); `GET /ready` (database-backed readiness); authenticated, access-restricted canary write/read endpoint or equivalent private test client; deterministic committed row IDs and checksums across reconnection and restore. Do not expose unauthenticated public write operations.
3. Set `database_access=true`; use least-privileged application credentials through an approved ECS Secrets Manager reference. Never put plaintext DB passwords, signed URLs, or test credentials in `container-workloads.auto.tfvars.json` or public evidence.
4. Review the **actual production-profile saved Plan**, including effective three-AZ networking, firewall endpoints, RDS Multi-AZ status, retention/protection, Backup and restore-test resources, ALB access logs, ECS health, image digest, and any optional WAF configuration. Keep `production_retirement_mode=false`.
5. Select ECS fixed capacity of at least three for the *three-AZ placement exercise*, then verify observed live task AZ distribution; three subnets and three tasks do **not** guarantee one task in each AZ. Rebalance/remediate only through reviewed changes. Scaling tests are conditional on an intentionally configured scaling policy.
6. Run existing workload validation/evidence (16 validators), verified ECS post-Apply acceptance, real HTTPS/ALB health, SQL smoke and persisted canary checks, access-log generation, and GuardDuty coverage checks. Document unavailable signals instead of treating green Terraform Apply as acceptance.

## Gate C — Controlled operational experiments

Every experiment requires a named start/stop, baseline steady-state record, isolated target, measured timestamps, independent observer, abort condition, and post-test restoration of healthy capacity.

| Experiment | Method / evidence | Exit criterion |
|---|---|---|
| Availability and placement | Capture real task IDs, AZs, desired/running counts, ALB target status, HTTPS success/errors, and SQL canary | Approved availability/placement criteria met, or documented gap |
| Task replacement | With stable baseline, deliberately stop **one** synthetic ECS task; observe replacement, ALB target behavior, task-deficit and unhealthy-target alarm transitions, and SecOps receipt | Healthy capacity converges; observed interruption and alarm latency recorded |
| Failed application rollout | Reuse M2's bounded release-acceptance procedure under the production profile, with a reviewed bad synthetic digest and a known healthy fallback | Apply gate refuses false acceptance; rollback/healthy restoration independently observed |
| RDS Multi-AZ failover | After seeding a committed canary and recording initial DB state, use a separately authorized RDS DB-instance **reboot with failover**; continuously observe SQL read/write recovery, client reconnect, RDS events, DNS behavior, and committed-row checksum | No lost **committed** canary rows; measured outage/reconnect within approved bounds or reported as a gap |
| Database backup restore | Confirm a completed, eligible recovery point and an approved **isolated** manual/restore-testing target. Restore without modifying source RDS, check seed row/checksum, demonstrate approved app/client reconnection path, measure elapsed duration, and delete/retain the temporary instance by disposition | Verified recoverable SQL canary with an independently measured restore duration; no remaining unapproved restore instances |
| Detection and notification | Inspect CloudWatch alarm coverage for ECS/ALB, RDS health/capacity, backup/restore failures, and relevant event subscriptions. Exercise real signals where safe; verify actual SNS delivery to the authorized SecOps recipient | Alert condition, alarm transition, delivered message, receipt timestamp, and cleanup documented; gaps become targeted M3 remediation |
| Evidence retention | Store sanitized test results outside the disposable workload; verify selected archive objects, checksums, KMS decrypt rights, retention decision, and retrieval after workload teardown | Required evidence remains readable independently of the retired environment |

For the current `aws_db_instance` Multi-AZ configuration, AWS documents an authorized `reboot-db-instance --force-failover` path. Do not confuse this with the different Multi-AZ **DB cluster** failover API. This operation interrupts database connections; do not run outside an explicitly approved disruptive test. See [AWS RDS failover](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html) and [RDS reboot](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RebootInstance.html).

The weekly AWS Backup restore-testing schedule may not execute during a short-lived staging window. A configured schedule is **not** evidence of a completed recovery. Choose a separate authorized restore test or a documented test window with a real recovery point. See [AWS Backup restore testing](https://docs.aws.amazon.com/aws-backup/latest/devguide/restore-testing.html).

**Monitoring-review candidates, not preapproved code changes:** RDS capacity and connection health, important RDS events/failover, AWS Backup job failures and restore-validation failure, app-level SQL health, and prolonged ALB 5xx/availability anomalies. Confirm current ownership, signal quality, thresholds, alarm cost/noise and integration before adding any baseline alarm. Retain 16 existing top-level validators; extend focused checks rather than creating another validator uncritically.

## Gate D — Production-profile retirement and independent audit

1. Record evidence/log-key dispositions **before** preparing deletion. Secure approved archives outside the workload's log buckets and encryption-key lifecycle.
2. Follow [Production Retirement](../production-retirement.md): normal production → reviewed retirement-mode Stage-1 Apply → saved-plan and readiness checks → explicitly approved ECR/Backup durable cleanup → separately approved final Terraform Destroy. Do not simply run the M2 development-profile destroy procedure.
3. Verify expected RDS final snapshot and retained native automated backups separately; audit all recovery points, ECR images, ALB/central log buckets, KMS keys, cloudwatch groups, and costs. Delete retained durable assets only according to independent explicit authorization and a usable-key/retention decision.
4. Rerun a **read-only** AWS residual inventory after Destroy. Record exceptions, cost owner, and evidence archive retrieval/decryption result. Complete M2's independent residual check if still open, but distinguish old and new test artifacts.
5. Document every test as `Pass`, `Fail`, `Not Run`, or `Not Applicable` with timestamp and explanation. Do not predeclare `Complete` before evidence is reviewed.

## Evidence register and exit decision

Record a private run directory with original AWS/Actions evidence and a sanitized public index. Each result includes source SHA, image digest, environment/profile, observer, UTC time, expected vs observed values, alarms/events, SHA-256 digest of raw files, and the decision. Never commit sensitive account identifiers, credentials, internal endpoints or raw security events to the public repository.

The M3 exit package must contain:

- Actual production-profile Terraform Plan/Apply/Destroy run links, config and immutable image digest.
- 16-validator evidence summary, ECS placement, task recovery, ingress and SQL transactions.
- RDS forced-failover measured timings and committed-canary integrity, plus independent backup restore/SQL verification.
- Confirmed SecOps delivery and monitoring gaps, with reviewed narrow fixes or documented owner-approved exceptions.
- Retained evidence decrypt/retrieval proof, production-retirement approvals, AWS residual-resource disposition, and final cost review.
- Maintainer approval of measured acceptance against the **preapproved** thresholds, not against retrospectively chosen targets.

**Status convention:** Design/approval work can be `In progress` while live qualification remains `Not Run`. No live resource, alarm, SQL, failover, backup restore, or teardown result is claimed by this plan.
